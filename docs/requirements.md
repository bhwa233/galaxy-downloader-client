# ·Galaxy Downloader 需求文档

本文是客户端的功能全集：第 2 节按主题列出全部功能，每条标注状态；第 3 节是明确不做的部分。

第 2 节里的标记有三种：**✅ 对应仓库里的实现，并且验证过**，是事实不是计划；**⚠️ 代码已经写了，但没有对着真站验证过**——这类一律写成「响应形状不符就放弃、把地址交回引擎」，所以猜错的代价是回到没有它时的行为，不会列出一份错的列表；**⬜ 是确定要做、还没有代码**（第 2 节现在已经没有 ⬜）。**2.10 是调研得来的候选功能，只表示值得讨论，不代表已承诺。** 各平台的测试链接集中在 `test-links.md`。两块带实施细节的另有专文：合集与列表见 `collections-and-pages.md`，封面与音频见 `covers-and-audio.md`。

## 1. 定位与原则

媒体下载管理器，只服务于媒体解析与下载。

- **本地优先**：解析、下载、登录态读取、文件保存全部在本机完成，不依赖任何远程解析服务
- **如实报错**：拒绝就报拒绝。不把"平台不支持"包装成"内容较少"，不把解析失败说成下载失败

## 2. 功能全集

### 2.1 平台支持

一级平台一律要求**单条链接 + 主页批量**，没有例外。主页批量的对象指的是各自平台上承载内容列表的那一层，不是首页推荐流。

| 平台 | 内容形态 | 主页批量的对象 | 现状 |
| --- | --- | --- | --- |
| 哔哩哔哩 | 视频、分P、合集、追番追剧 | 投稿、合集、系列 | 单条与投稿已有 |
| 抖音 | 视频、图文、短剧、放映厅 | 作品、喜欢、推荐、合集 | 单条与作品已有 |
| 微博 | 视频、图文 | 用户主页 | 单条已有 |
| 微信公众号 | 图文、图片、音频（音乐卡片）、视频 | 历史消息列表 | 单条已有 |
| YouTube | 视频、Shorts、播放列表 | 频道、播放列表 | 已有 |
| X | 视频、图文、GIF、长文 | 用户时间线 | 单条已有 |
| Instagram | 视频、图文、Reels | 用户主页 | 单条已有 |

内容形态一列是 2026-09-22 逐个平台在真实浏览器里核对过的结果，不是推断。微信公众号另外用两篇真实文章核对过**文章内部**的媒体构成，见 2.2。

X 的长文归到"图文"处理；**短剧、Shorts、Reels** 是新的内容类型，不能并进现有任何一项，见 2.2。专栏、收藏夹、头条文章、超话、节目、帖子（社区）不在范围内，见第 3 节。直播也不在范围内，见第 3 节。

一级平台之外，yt-dlp 覆盖范围内的其他站点只承诺单条链接，主页批量不支持——那些站点数量不封顶，逐个适配主页不是这个客户端要做的事。

### 2.2 解析

✅ `electron/services/parser.ts` 是唯一分流点，三条路线按顺序选择：

| 路线 | 触发条件 | 执行位置 |
| --- | --- | --- |
| 主页列表 | 地址被某个列表适配器认领 | 应用内浏览器的隐藏窗口 |
| 直连解析 | 其余地址 | 本地 yt-dlp |
| 浏览器兜底 | 直连失败且失败原因像登录或风控 | 应用内浏览器 + yt-dlp |

- ✅ **主页列表适配器**（哔哩哔哩投稿、抖音作品、YouTube 频道）：列表接口由页面自己发出，请求的 cookie、`Origin`、`Referer`、客户端提示、TLS 指纹全部由浏览器供给
- ✅ **加载更多**（2026-09-23 由页码翻页改来）：列表按页取，下一页追加到已加载的内容后面，之前的条目与勾选都保留；窗口在页间复用（同一地址命中则跳过页面加载，实测省约 4 秒），5 分钟无操作后释放
- ✅ **预估大小**（2026-09-24）：每个档位带上下载大小（视频流 + 合并的最佳音频流），取平台给的准确值 `filesize`，没有就用估计值 `filesize_approx`，再没有就用码率 × 时长；另存总码率。单个视频显示所选档位的大小；列表（主页、合集、分P）用后台读到的第一个视频的档位码率 × 每条自己的时长估算。卡片与行里显示「约 X MB」，底部操作栏显示已选合计，随画质切换更新；算不出来的不显示。实测：YouTube 单条 1080p「约 190.8 MB」（视频流 182 MB 为平台准确值 + 音频）；哔哩哔哩给的是估计值；X 部分格式给估计值、都有码率；抖音在客户端里走浏览器兜底没有格式信息，不显示。列表估算与实际可能差 ±30%。**2026-09-24 修正**：原来每档都按 AVC 变体算大小，而「默认画质」下载时引擎取的是它自己偏好的变体（哔哩哔哩是 HEVC，YouTube 是 VP9），同分辨率下可小一半：曾显示 72.8 MB、实际下载 33.9 MB。现在每档另记「默认下载会取的变体」（yt-dlp 同一档里排最后的那个）的大小与码率：选了具体档位按 AVC 算，默认画质按偏好变体算。复核：哔哩哔哩 BV1bK411W797 p1 显示 13.2 MB、实际 13,830,346 字节（13.2 MiB）；YouTube 仍偏大约 18%（默认取的 616 只给声明码率，不给大小）。**逐档复核**（手动选档位、按队列同样的格式串真实下载）：哔哩哔哩 1080P / 720P60 / 480P / 360P 误差 -0.2% ~ -1.1%，YouTube 1080p / 720p / 480p / 360p / 240p / 144p 误差 0% ~ 0.4%；会员档（4K、1080P60）需登录态，复核脚本不带登录，未能对比。复核中发现并修了一个 bug：YouTube 360p 档原来取的是音画合一的旧格式 18，下载会话拿不到它，选 360p 实际下到了 1080p；现在每档优先取纯画面的 AVC 流再合并最佳音轨，360p 为 134，实测下到 640×360、17.4 MB，与显示一致
- ✅ **下载内容**（2026-09-24，取代原来的「仅音频」「仅封面」两个勾选框）：底部操作栏的多选下拉，视频 / 音频 / 封面可任意组合，至少选一个，每次解析回到「视频」。每种内容各成一批任务（批次名分别为「<标题>」「<标题> · 音频」「<标题> · 封面」）；图片条目没有音频、没有封面地址的条目没有封面，这些会跳过并在操作栏里写明，不再像以前那样整批报「图文不能转换为音频」。画质只对视频生效，未选视频时禁用；按钮为「下载 N 项 / N 个音频 / N 个封面」，组合时为「下载 N 个文件」。封面任务直接下载记录下的封面地址，不重新解析、不经过引擎。右键菜单「下载这一项 ›」子菜单为视频（图片条目为图片）/ 音频 / 封面。音频格式不在这里选，在 设置 → 文件与媒体「音频格式」，新增「最高音质（不转码）」并设为默认（yt-dlp `preferredcodec: best`，保留平台原始音轨）。实测：哔哩哔哩主页勾 2 条选「音频 + 封面」，得到 2 个 m4a（原始 AAC，未转码）与 2 张 JPEG，分在两个批次
- ✅ **结果卡片右键菜单**（2026-09-24）：下载这一项 / 仅下载音频（视频才有）/ 选中或取消选中 / 选中到这里 / 复制链接 / 复制标题 / 复制封面地址 / 保存封面… / 打开原网页；付费集只保留复制与打开。「下载这一项」按当前画质单独入队，不改动已勾选的。「保存封面」弹系统另存为对话框，经客户端自己的会话下载（这一项没有自动化验证）。另支持 **Shift+点击连续选择**：从上一次勾选的卡片到这一张全部勾上，与「选中到这里」同一逻辑。解析历史的每一行也加了右键菜单：重新解析 / 复制链接 / 打开原网页 / 删除这条记录。下载任务列表原本就有右键菜单
- ✅ **解析历史**（2026-09-24）：新建任务页下方列出解析成功的链接，最新在前，同一地址只留一条（再次解析移到最上面），最多 50 条；只记成功的。每条显示封面、标题、平台 · 类型（单条 / 主页 / 合集 / 分P）· 条目数 · 时间，操作有「重新解析」（直接开始解析）、复制链接、打开原网页、删除；顶部有标题搜索与「清空」（先确认）。有解析结果时折叠为最近 5 条，其余「显示更多」。存在客户端自己的数据文件里，不上传；设置 → 常规「保存解析历史」可关闭记录（默认开）。客户端实测：六种链接各解析一次得 6 条、类型与条数正确，折叠 5 条 / 展开 6 条，搜索与重新解析都工作
- ✅ **画质档位**（2026-09-23）：档位名按平台叫法——哔哩哔哩的抽取器不给名字，按高度与帧率还原成「1080P60 高帧率 / 1080P 高清 / 720P 高清 / 480P 清晰 / 360P 流畅 / 4K 超清 / 8K 超高清」，YouTube 用它自己的 `1080p`、`720p60`。同一档有 AVC / HEVC / AV1 多种编码时只留 AVC 一个：兼容最好，而且它的格式编号跨视频一致（哔哩哔哩 720P 恒为 `30064`，YouTube 1080p 恒为 `137`）。音频格式不进画质列表，走「仅音频」。**列表（主页、合集、分P）的条目本身没有档位**，解析完后在后台读第一个视频一次，把它的档位给整批用；某个视频没有所选档位时按最高画质下载并在任务日志里注明，不再报「所选画质已失效」。实测：`space.bilibili.com/365290` 解析后 2 秒出现五档，选 720P 高清下载两条，都是 1280×720 H.264 + AAC；23 分P 的 `BV1bK411W797` 读到 720P / 480P / 360P 三档
- ✅ **全选**：勾选所有已加载且可下载的条目（付费集除外），与「只看」筛选联动；实测加载三页 48 项后全选勾上 48 项
- ✅ **单作品解析**：yt-dlp 扁平解析，条目缺少元数据时自动改为完整解析
- ✅ **直链兜底**：yt-dlp 拒绝的地址，若 HEAD 响应是 video/audio/image 类型，按直链下载
- ✅ **图文**：页面里的图片按 HTTP 下载，视频交给引擎

**合集与分P**（实施清单见 `collections-and-pages.md`）

- ✅ 哔哩哔哩：分P 视频、视频所属合集、合集与系列链接
- ✅ 抖音：作品合集（`douyinCollection`，`/collection/<mix_id>` 实测 6 条）、作品页归属合集（`douyinVideo`）、用户页按 `showTab` 分流到喜欢与推荐、`user/self`。2026-09-23 在客户端里逐条跑过，改了三处：
  - **推荐的接口原来猜错了**：`aweme/user/recommend/` 回 `404 Unsupported path(Janus)`；页面自己调的是 `aweme/v1/web/familiar/recommend/feed/`，形状与作品接口一致。对方隐藏推荐时回 `aweme_list: null`（登录也一样，网页显示「推荐内容不可见」），现在如实说「对方没有公开推荐列表」，不再报成登录问题
  - **`user/self` 原来会列出别人**：从页面 storage 取第一个 `MS4wLjABAAAA…`，而 storage 里的 `LOG_TRACE` 存着别的用户，实测列出的是「天爱Talk的作品」。现在和页面一样调 `user/profile/self/` 取 `user.sec_uid`，实测列出本人作品
  - 合集的标题与落盘目录改用合集自己的名字（`mix_info.mix_name`），原来是「<作者>的合集」——同一作者的每部短剧都会落进同一个目录

- ✅ YouTube 播放列表与 Mix 今天已能用；100 条截断不再静默，撞上限的结果会写明「只列出了前 100 条」
- ✅ 视频链接的二选一：多P 走分P 列表，属于合集则列出合集条目，两者都没有时回落到引擎直解
- ✅ 展示：同一结果里既有分P 又有合集时以标签页切换，选择跨标签页保留
- ✅ 落盘：合集与分P 存入以合集名命名的子目录，由新设置项 `organizeByCollection` 控制（默认开）

**主页批量**

- ✅ 七个一级平台的验收口径完全一致：**单条链接能下载，主页能批量列出**。平台清单见 2.1。**主页批量七家都已在客户端里验证**（2026-09-23，X、Instagram、微博三家在登录后）。微信公众号只有「合集」可用（历史消息列表在网页上不存在，见下）。X 纯图片帖、Instagram 图文帖的单条下载也已补上并真实下载验证，见下
- ✅ 今天已有主页批量的只有三家：哔哩哔哩（投稿）、抖音（作品）、YouTube（频道）
- ✅ 新增四家都已在客户端里验证（2026-09-23），全部按「响应形状不符就放弃、把地址交回引擎」写：
  - ✅ **微博** `listings/weibo.ts`，走 `ajax/statuses/mymblog`。页面自己的请求带 `X-Requested-With: XMLHttpRequest` 与 `X-XSRF-TOKEN`（取自可读的 `XSRF-TOKEN` cookie），不带就回 `403 Forbidden` 的 HTML，已补上。登录后客户端列出「生草字幕组的微博」第 1 页 18 条、第 2 页 12 条全新，每条有封面与 `weibo.com/<uid>/<bid>` 链接。未登录时页面自己的请求也只得到 `{"ok":0,"message":"前方有点拥堵，请登录后使用"}`，这种情况放弃、交给引擎（引擎匿名能列 100 条，但不分页）
  - ✅ **X** `listings/x.ts`，走 GraphQL `UserMedia`。两样东西从页面里读而不是在这边复现：CSRF 令牌取自 `ct0` cookie，GraphQL 的 operation id 从页面自己的脚本包里找（它每次发版都变）。为此给 `PageRequest` 加了一个 `evaluate`——用途是「问页面它已经知道什么」，不是驱动页面，滚动列表这件事仍然不做。未登录报「没有请求令牌」。**2026-09-23 登录后实测**：原来每个主页都放弃接管——读脚本包用的是带凭据的页内 fetch，而 `abs.twimg.com` 不回 CORS 头，带凭据的请求被浏览器直接拒掉，一个 id 都没读到；兜底于是把页面嗅到的视频流当条目，封面全是 X 的默认分享图。现在在页面里用不带凭据的 fetch 读脚本包，只把 id 传回来。登录后的 X 仍是旧前端（`responsive-web/main.*.js`），`UserTweets` / `UserByScreenName` 都在里面，不带 X 自己的 `x-client-transaction-id` 也回 200。原先用 `UserTweets`，每页 20 条里多数是纯文字帖，被过滤后第 1 页只剩 3 条；**已改用 `UserMedia`（主页的「媒体」标签页），只返回带图片或视频的帖子**。客户端列出「FinanceYF5 的媒体」，3 页分别 13、14、10 条，全部不重复，每条有自己的封面、正文标题与 `/status/` 链接。（页面默认标签调的是 `UserOriginalsTimeline`，也实测可用，但同样混有纯文字帖。）**未登录时 X 给的是另一套前端**（`abs.twimg.com/x-web/…`，Relay + TanStack Router，时间线服务端渲染，页面里没有 queryId），适配器在这种情况下只能放弃
  - 兜底（页面嗅探）对上封面：嗅到的视频流按地址里的媒体 id（`amplify_video/<id>/`）合并——一个 X 视频实测会被嗅到 9 个地址（主播放列表、各清晰度、各初始化分片），现在合成一条、保留主播放列表；再按同一个 id 对上页面里 `<video poster>`（`amplify_video_thumb/<id>/`），拿到这条的封面、所在卡片的 `/status/` 链接与正文。**这部分没有在客户端里端到端验证过**：登录后 X 主页已经不走兜底了；poster、链接、正文的结构是在未登录的新前端上用 Chrome 核对的
  - ✅ **X 图片帖、Instagram 图文帖的单条下载**（2026-09-23 加单帖适配器）：原来引擎只认视频、兜底只在文章页收图片，X 图片帖报「页面没有提供可下载的媒体」，Instagram 多图帖兜底出 30 条同封面。现在 `xPost`（X 的 `TweetResultByRestId`，帖子页自己调的查询）与 `instagramPost`（`api/v1/media/<id>/info/`，帖子页自己调的接口；id 由 shortcode 按 base64url 换算）读出帖子里的每个文件：图片取原图（X 加 `name=orig`），视频取直链 mp4，一个文件一条、按 HTTP 下载。帖子里一张图都没有就是视频帖，放弃并交给引擎（保留画质选择）。单帖适配器在任务重新解析时也会运行，所以主页列表里的图文帖入队后同样下得下来。真实下载验证：X 图片帖 2 张原图、Instagram 多图帖 7 张图 + 1 段视频、从 X 主页列表挑的图片帖 1 张，全部落盘且格式正确。Instagram 那段视频只有画面没有音轨，原片是否静音没有核实
  - 顺带修的两处（都是这次真实下载才暴露的）：**所有带 Referer 的 HTTP 下载原来都会失败**——会话的 `fetch` 遇到手动设置的 `Referer` 请求头直接报 `net::ERR_BLOCKED_BY_CLIENT`，公众号图片也走这条路；现在改由请求的 `referrer` 选项传。**列表窗口原来会被并发读取互相销毁**——下载任务重新解析帖子与用户的下一次解析同时用那一个窗口，报「Object has been destroyed」；现在读取排队，一次一个。单帖的解析结果也会缓存，一个 8 张图的帖子拆成 8 个任务只读一次
  - ⚠️ **登录入口**：设置里的「打开登录窗口」没有待登录地址时打开的是空白页，窗口没有地址栏。所以一个平台只要匿名也能解析成功（例如微博主页交给引擎后能列 100 条），用户就没有入口去登录它
  - ✅ **Instagram** `listings/instagram.ts`，**2026-09-23 登录后重写**。原来按文档写的 v1 接口在网页端已经不能用：`web_profile_info` 与 `clips/user` 回 429，`feed/user` 回网页外壳。页面自己读作品网格走的是 GraphQL：作品是 `PolarisProfilePostsQuery`，Reels 是 `PolarisProfileReelsTabContentQuery`，都 `POST /graphql/query`、按 `doc_id` 调。实测只要 `doc_id` + `variables`，加 `X-CSRFToken`（可读 cookie）与 `X-IG-App-ID` 两个头就回完整结果，页面其余二十来个表单字段都不需要；节点就是原来 v1 的媒体结构。`doc_id` 每次发版会变，从页面已加载的脚本里读（`<查询名>_instagramRelayOperation` 模块导出的就是它），Reels 要的用户数字 id 页面 HTML 里写着 `"profile_id"`。翻页：作品传 `after` + `first`，Reels 只传 `after`。客户端列出 `@instagram` 的作品与 Reels，各连翻 3 页、每页 12 条全新，每条有自己的封面与 `/p/`、`/reel/` 链接。Reels 查询不返回正文，标题只能是「Instagram <code>」。未登录时这些接口回 `require_login`，报需要登录
  - ✅ **微信公众号** `listings/weixin.ts`，读**合集**（`mp/appmsgalbum`）。2026-09-23 实测：接口形状与代码一致（`base_resp.ret`、`getalbum_resp.article_list`、`continue_flag`，标题在 `base_info.title`），匿名可用，客户端列出 8 篇与 65 篇两个合集。**翻页原来写错了**：用的是 `begin_msgid=(页码-1)×10`，这个偏移量回的是没有 `article_list` 的空响应，第 2 页会放弃；页面自己发的是上一页末条的 `begin_msgid` + `begin_itemidx` 游标，已改成这样，实测连翻 3 页 30 篇无重复。**历史消息列表不做，因为网页上根本没有这个东西**：它是微信客户端内的一个视图，浏览器拿不到任何地址能到那里。粘公众号主页链接会直接说明这件事并指向合集链接，而不是掉进一条本来就服务不了它的路线再报一个像登录问题的错
- ✅ **每个平台都要有自己的主页列表适配器，一个也不能少，而且必须写在客户端里。** yt-dlp 没有"主页列表"这一层——它解析单个作品，或它自己认识的播放列表，别人的主页不在它的能力范围内。所以主页批量没有任何一部分能外包给引擎，工作量与平台数成正比，指望一个通用实现覆盖多家是不成立的

**还差三家，以及为什么现在写不了**（与 `collections-and-pages.md` 第 8 步同一个理由：形状要先在应用内浏览器里抓到，才能照着写）：

| 平台 | 卡在哪 |
| --- | --- |

- ✅ 批量口径已经定下，对所有平台一致，不允许一个平台一套（逐项状态见表内）：

| --- | --- |

**微信公众号的文章结构**

- ✅ **图片**在主文档里（`<img data-src>`，懒加载），走现有图文的 HTTP 下载路径。只按公众号这一个域名开启这套扫描：对普通媒体页做同样的扫描会把缩略图和页面装饰当成作品，而且一旦返回了图片就不会再走引擎解析。声明宽高小于 200 的图（头像、二维码、统计像素）跳过，没声明尺寸的保留
- ✅ **音乐在网页上拿不到**（2026-09-23 在 Chrome 里对 `/s/kgrMPE4Sl6oXVTYGKCnzdQ` 实测）。原先「音乐卡片是 iframe」的判断是错的：卡片是主文档里的自定义元素 `<mp-common-clmusic>`（带 shadow root），属性里只有 `music_name`、`singer`、`albumurl`、`duration`、`listenid`，没有任何音频地址。点「播放」弹出「即将前往微信打开此文章」；取曲目的接口 `mp/finder_music_appmsg`（POST `id0=<listenid>`）回 `{"ret":-3,"errmsg":"no session"}`——要微信客户端的会话，浏览器没有。所以解析时进子框架取 `<audio>` 的那段代码对音乐卡片不会起作用；它对别的嵌入媒体无害，留着

### 2.3 下载与队列

- ✅ 并发 1–4 个任务，全局限速与单任务限速，超时与重试次数可配
- ✅ 断点续传：引擎保留 part 文件，输出路径每次一致，重试只补缺失部分
- ✅ 分段请求：`http_chunk_size` 10 MiB，一次中断只损失一个分段而不是整次传输
- ✅ **自动续传**：下载中断后自行重试，间隔 20 秒、60 秒各一次；等待期间任务保持失败态并在错误信息里写明何时重试；完成或手动重试会把计数清零
- ✅ **重复排队保护**：同一地址同一条目若已在排队、下载或暂停，不会再建一个任务
- ✅ 音视频分离时自动合并；字幕可嵌入、可存为独立文件、可关闭，语言可指定，可回退到自动生成字幕
- ✅ 仅音频下载：`bestaudio` + 提取为 mp3/m4a/flac
- ✅ 文件命名三种模板，可按平台建子目录

封面与音频的追加（设计与结论见 `covers-and-audio.md`）：

- ✅ **封面下载**，两种形态都有：随任务自动存（新设置 `saveThumbnail`，默认关，下载视频时顺带把封面存成同名图片），与任务右键「下载封面」（点了才存一张，不受任务状态限制）
- ✅ **封面嵌进视频文件**：下载视频后把封面写进视频文件本身，让它成为视频的封面图，由新设置 `embedThumbnailInVideo` 控制（默认关）。**mp4/mkv 上各播放器的实际表现仍未实测**（见 `covers-and-audio.md` 第 4 节）
- ✅ **音频追加**：任务右键「下载音频」，对一个已存在的视频任务再建一个音频任务，原任务与原文件不受影响
- ✅ **音频嵌封面**：仅音频下载时把封面嵌进音频文件，由新设置 `embedThumbnailInAudio` 控制（**默认开**）
- ✅ **重复排队保护的键把"仅音频"算进去了**：对一个正在下载的视频任务点「下载音频」不再被挡掉
- ✅ 合集与分P 的任务落到以合集名命名的子目录，与按平台建目录叠加时顺序为 `<下载目录>/<平台>/<合集名>/`

### 2.4 任务管理

- ✅ 状态：等待中、下载中、已暂停、已完成、已取消、失败
- ✅ 单任务操作：暂停、继续、重试、取消、单独限速
- ✅ 批量操作：开始全部、暂停全部
- ✅ **批次**：一次解析入队形成一个批次（`job.batchId`），批次可整体暂停、继续、重试、取消、删除，批次内仍保留单任务操作。任务卡片上写明所属批次，右键有「整批」子菜单。
- ✅ **每个媒体文件算一个任务**。一个作品里有几个媒体文件，要把那个作品解析过才知道，所以拆分发生在任务真正开始下载的那一刻：本任务留下第一个文件，其余各自成为同批次里的新任务。它们解析的是同一个作品，由 `Parser` 的两分钟单作品解析缓存兜住——否则九张图的作品要解析九次
- ✅ 一次入队的规模上限在设置里（「单次批量上限」`batchLimit`，默认 20）；批量时可按 **只看视频 / 只看图文** 筛选。「最近 N 天」与结果区的临时上限 2026-09-23 按决定去掉
- ✅ **右键菜单**：复制链接、打开原网页、打开文件位置、复制文件路径、暂停/取消/继续/重试、删除记录
- ✅ 右键菜单新增两项：「下载封面」「下载音频」
- ✅ **删除**：单条删除与清理已结束记录，都可选择同时删除文件；文件走系统回收站而不是直接抹除；未记录在案的残留文件按任务自己的文件名前缀在任务目录内查找
- ✅ **任务详情**：概览、文件列表、活动日志三个标签页
- ✅ 列表支持搜索、按媒体类型与平台筛选、排序、列表/卡片两种视图
- ✅ 侧边栏按全部、下载中、已完成分组，带计数
- ✅ 历史与设置持久化，可选启动时恢复上次未完成的任务

### 2.5 登录与身份

- ✅ **两跳认证**：先尝试读取系统浏览器（Chrome/Edge/Firefox）的登录态；读取失败（系统加密、浏览器占用）时静默跳过，不影响公开内容

#### P0：优先讨论

**1. 下载归档与增量更新**

- 对每个来源（频道、主页、播放列表、合集）保存平台稳定 ID、最后扫描时间、游标与已下载记录；再次扫描时只列出或加入新内容。
- 已下载内容在解析结果中明确标记“已下载 / 文件缺失 / 来源已删除”，用户可选择跳过、重新下载或仅修复缺失文件。
- **结论：归档按平台内容 ID 去重**，不把"视频/音频、质量、字幕、封面"拆成独立产物版本。同一内容换了画质不算新内容，用户可以对单条或整批执行“强制重新下载”。
- 归档记录随历史一起持久化，可导出、导入和清空；任何自动跳过都要在结果区说明原因。

**2. 来源监控（订阅）**

- 用户可保存一个主页、频道、播放列表或合集为来源，手动刷新或按设定间隔扫描；扫描结果沿用现有列表选择与去重语义。
- 每个来源可设置默认质量、仅音频、字幕、落盘目录和是否自动入队。**结论：允许按来源自动入队**——首次加入来源时先让用户确认，之后按该来源的规则自动入队。
- 监控必须在本机运行。**结论：应用退出后监控与定时下载彻底停止**，不做后台常驻服务；下一次启动时显示错过的扫描和新增数量。
- 来源失效、登录过期、权限变化要分别显示，不能把来源变空当成“没有新内容”。
- 每个来源可设关键词过滤、自动标签、只取最新一条、自定义落盘目录与文件名模板——避免长期订阅每次都产生一堆待选条目。

**已评估并放弃：把 RSS 当作订阅来源。** 曾经考虑用它省掉逐个平台写适配器，实测后放弃。结论记在这里，避免以后重新调研一遍：

| 平台 | 官方 feed | 依据 |
| --- | --- | --- |
| YouTube | **有** | `youtube.com/feeds/videos.xml?channel_id=<UC…>` 实测 200、Atom、29,879 字节；旧的 `?user=` 形式已 404 |
| 哔哩哔哩 | 无 | 官方从未开放；`rss.bilibili.com` 域名 DNS 不解析 |
| 微博 | 无 | `rss.weibo.com` 域名 DNS 不解析 |
| 微信公众号 | 无 | 只能靠第三方（Wechat2RSS、WeWe RSS 等；后者的仓库 2026-01 已归档） |
| 抖音、微信视频号、X、Instagram | 无 | 未见官方 feed；第三方路由需要登录态，或依赖外部服务 |
| 播客、博客、新闻站、论坛 | 普遍有 | RSS 是这些内容形态原生的分发方式 |

放弃的理由有两条：一，**7 个一级平台里只有 YouTube 一家适用**，其余六家官方都没有 feed，只能靠第三方聚合，而那是外部服务，与"本地优先"冲突；二，把 RSSHub 一类生成器跑在本机虽然绕开了外部服务，但要长期维护各平台的路由规则，平台一改版这些路由同样会坏——本质还是"一平台一份工作"，只是从逆向平台接口换成维护别人的逆向成果，并不省事。**主页批量一律自建适配器，见 2.2。**

**3. 批量输入与任务分组**

- 新建任务支持多行 URL、文本文件、拖放文件；每行可带标题注释，空行和注释行忽略。
- 输入批量解析前显示 URL 数量和重复数量；与现有队列去重合并，不把解析失败的地址静默丢弃。
- 一次导入形成一个**批次**（定义见 2.4），对批次整体暂停、继续、重试、取消和删除；批次内仍保留单任务操作。入队前可设这一批的规模上限。

**4. 可解释的格式与下载预设**

- 解析结果展示可用格式的关键字段：容器、编码、分辨率、帧率、HDR、码率、音频编码/语言、预计大小（平台提供时）。不能只显示“720p”。
- 提供可命名的下载预设，至少覆盖“最佳兼容性、最高画质、限制分辨率、仅音频、保留原始容器”；预设可按平台和来源覆盖，但单次任务可改回默认值。
- 预设必须展示“没有满足条件时的回退规则”，格式不可用时如实提示，不自动降到用户未允许的质量。
- 容器要能选：自动（MP4/MKV）、MP4、MKV、WebM、原始容器；音频可另存为独立文件。

**5. 存储与产物安全**

- 入队前检查目标目录可写、剩余空间和文件名冲突；预计大小未知时明确标注“无法预估”，不能假装检查通过。
- 用户选择冲突策略：跳过、覆盖、另存为新文件；断点文件和最终文件的归属要能在任务详情中看见。
- 下载完成后可按来源提供的校验值校验；没有校验值时只报告“未提供校验值”，不声称已验证完整性。

#### 原 P1 里已排除的条目

以下几条原本是候选，已决定不做，理由记在这里：

- **元数据与附属文件**：不做。不保存 `.info.json`、描述文本这类 sidecar，也不把标题、作者、描述嵌进媒体。**注意它与封面、字幕是两回事**：封面（存一份 / 嵌进媒体 / 右键下载）与字幕（嵌入 / 独立文件）仍按 2.3 处理，不受这条影响。
- **章节与时间段**：不做。章节展示、按章节拆分、起止时间段下载整条不列入。本客户端只做媒体本身的下载。
- **网络策略**：代理不做，不提供 HTTP/HTTPS/SOCKS 代理配置（用户决定"先不做"）。分片并发、强制 IPv4/IPv6、分片重试这几项不在本轮单独列，归入现有「下载」设置的后续细化。
- **本地转录与 AI 处理**：不做。这是从 VidBee 借鉴来的能力域——本地语音识别、说话人分离、转录稿搜索与导出、转录稿上的 AI 提示——但它会把产品从"媒体下载管理器"变成"媒体资料库"，超出本项目定位；其中的云端 provider 还与 §1 的"本地优先"正面冲突。

#### 与本项目既有边界的冲突

调研 VidBee 时看到三处能力**明确不在本项目范围内**，记在这里是为了以后不必重新判断：

- **浏览器扩展**：§3 已排除。
- **可独立部署的 Web / API 与 Docker 服务端**：与 §3 的"无界面服务端"排除冲突，也与 §1 的"本地优先"不一致。它的 Web 版本质是把服务端跑在 NAS 上、浏览器当客户端，那是另一种产品形态。
- **远程 AI provider**：转录稿会发往第三方。VidBee 自己也在文档里提示"想全本地就用 Ollama / LM Studio"，说明这个分界是公认的。
